# Промт для Claude Code: дашборд «Радар открытий»

Скопируй всё содержимое ниже как первое сообщение Claude Code в новом репозитории.
Перед запуском — прочитай блок «Что нужно подтвердить» в конце файла, там зависящие
от твоего решения пункты (помечены `[ПОДТВЕРДИ]`).

---

## 1. Контекст

Мы — департамент аналитики розничной сети (fuel retail, МагБургер, Братья Караваевы,
производство). Нужен внутренний веб-дашборд «Радар открытий»: он контролирует, вовремя
ли на точках («лавках») отмечаются сотрудники и водители при открытии, и насколько
наполнена витрина к 08:00 и в течение дня.

Цель — заменить ручную раскраску ячеек в Excel (см. `Витрины.xlsx`, лист «Все данные» —
это легаси-формат, который дашборд должен воспроизводить логически, но считать статусы
автоматически, а не руками).

## 2. Источники данных

### 2.1. Таблица отметок сотрудников (пример: `25_08__выходы.xls`)
Формат — старый `.xls`, колонки:
`Подразделение | Сотрудник | Должность | Подразделение сотрудника | Приход | Уход | Часов фактически | Часов ночь`

Наблюдение по тестовому файлу: колонка «Приход» почти всегда заполнена, «Уход» почти
всегда пустая (NaN) — то есть отметка на вход есть, отметка на выход в течение дня не
фиксируется системой доступа. Учитывай это в парсере, не полагайся на «Уход» как на
надёжное поле для этого источника.

Должности, встречающиеся в файле (бери как справочник ролей + маппинг на роль-класс):
`Повар`, `Повар-стажер`, `Кассир`, `Кассир - стажер`, `Бариста` (см. лист-фото ниже).
**Стажёры должны попадать в те же пороговые правила, что и базовая роль**, если не
указано иное — стажёр = «Повар»/«Кассир» с суффиксом статуса в UI, не отдельная колонка
времени.

### 2.2. Таблица отметок водителей (пример: `водители_25_08_.xls`)
Тот же формат колонок. Здесь **и «Приход», и «Уход» обычно заполнены** — то есть у
водителей другая специфика по сравнению с сотрудниками лавки.

### 2.3. Таблица наполненности витрины
Google Таблица (общий доступ на редактирование всему департаменту аналитики),
заполняется в течение дня вручную (числовое значение % или доля 0–1).
Обмен с сервисом — раз в 10 минут по крону + принудительное обновление по кнопке в UI.

## 3. Хранилище файлов (Приход/Уход)

**[РЕШЕНИЕ]**: используем **Google Диск**, не Яндекс Диск.
Обоснование: наполненность витрины уже в Google Таблицах → один сервис-аккаунт, один
API, одна авторизация вместо двух экосистем. У Google Drive API есть `modifiedTime` и
polling/watch-каналы, этого достаточно, чтобы поймать замену файла (файл заменяется
целиком, не добавляется — значит ищем по стабильному имени/ID папки, сортируем по
`modifiedTime desc`, берём последнюю версию).

Если это неверно (например, у отдела уже есть жёсткий процесс на Яндекс Диске) —
скажи Claude Code явно поменять коннектор, интерфейс парсинга это не затронет.

## 4. Правила статусов (красная/жёлтая/зелёная зона)

Источник — фото рукописного листа «Разбор открытий». Разобрано с фото, **часть цифр
читается неоднозначно от руки — сверь перед продакшеном**, я пометил `[ПОДТВЕРДИ]`:

| Критерий | 🟢 зелёная | 🟡 жёлтая | 🔴 красная |
|---|---|---|---|
| Приезд водителя | до 6:03 `[ПОДТВЕРДИ]` | 6:18–6:30 `[ПОДТВЕРДИ]` | позже / нет отметки |
| Вход — Повар | до 6:00 | 6:01–6:10 | 6:11 и позже / нет отметки |
| Вход — Кассир | до 6:50 | 6:51–7:00 (7:01–7:10 жёлтая по листу) `[ПОДТВЕРДИ]` | позже / нет |
| Вход — ЗД по залу (замдиректора по залу) | до 5:50 | 5:50–6:10 `[ПОДТВЕРДИ]` | позже / нет |
| Вход — Бариста | до 6:50 | 6:50–7:10 `[ПОДТВЕРДИ]` | позже / нет |
| Наполнение витрины | 95–100% | 85–94% | ≤84% |

**Другой график.** В сырых данных встречаются отметки прихода позже 08:00 — это не
опоздание, а сотрудники с иным графиком (не с открытия). Правило по умолчанию:
**если фактическое время «Приход» позже 08:00 → статус не считается по таблице выше,
сотрудник помечается отдельным нейтральным статусом «другой график» и не входит в
агрегаты 🔴/🟡/🟢 по умолчанию.** Порог 08:00 — не подтверждён документально, это моя
интерпретация твоей формулировки, см. `[ПОДТВЕРДИ]` в конце.

⚠️ Риск этого правила: сотрудник на обычном открывающем графике, который реально
опоздал на 2+ часа (то есть отметился в 08:15), тоже попадёт под «другой график» и
выпадет из красной зоны — то есть реальное опоздание молча спрячется. Часовой порог
без явного источника правды по графикам — это заплатка, а не решение. Правильный путь
— отдельный справочник «сотрудник → тип графика» (обычно есть в HR-системе/1С ЗУП),
тогда исключение строится по факту, а не по эвристике времени. Если такой справочник
есть — дай Claude Code доступ к нему, время 08:00 как эвристика тогда не нужна вообще.

Реализуй пороги **не хардкодом в компоненте, а конфигом** (JSON/таблица в БД,
редактируемая из админки или хотя бы из `.env`/`config.ts`), потому что:
1. я не уверен в части цифр выше;
2. пороги реально могут отличаться по ролям и меняться со временем — тогда не
   потребуется деплой ради правки константы.

## 5. Алгоритм при отсутствии отметки

0. Приход зафиксирован, но позже 08:00 → см. правило «Другой график» в п.4. Статус
   «другой график», не участвует в агрегатах по умолчанию. Выполняется раньше всех
   остальных пунктов — если сработало это правило, дальше по цепочке не идём.
1. Нет отметки вообще (ни прихода, ни ухода) → статус = **красный**, без исключений.
2. Есть отметка «Уход», нет отметки «Приход» (актуально в первую очередь для
   водителей, у сотрудников поле «Уход» почти всегда пусто, см. п.2.1) →
   **расчётное время прихода = Уход − 30 минут** (30 мин — время приёмки).
   Пример из ТЗ: нет прихода, уход 07:40 → считаем приход 07:10, дальше сравниваем
   07:10 с пороговой таблицей как обычно.
3. Есть и приход, и уход → используем фактический «Приход».
4. Логируй, какой из трёх случаев сработал (реальная отметка / расчёт −30 мин /
   отсутствие данных) — это должно быть видно при раскрытии карточки лавки на
   конкретный день, иначе аналитик не отличит «реально опоздал» от «система досчитала».

## 6. Функциональные требования к дашборду

### 6.1. Общий дашборд (главная страница)
- Сводка по всей сети: сколько лавок в 🟢/🟡/🔴 по каждому критерию отдельно
  (приезд водителя / вход по каждой роли / наполнение витрины) и агрегированный
  статус лавки (обсуди с бизнесом правило агрегации — по умолчанию: **самый плохой
  статус из критериев = статус лавки**, но вынеси в конфиг).
- Топ проблемных локаций (анти-топ 🔴) — как в легаси-листе «ПРОБЛЕМНЫЕ ЛОКАЦИИ»
  в `Витрины.xlsx`.
- Где «больше всего западает» — разрез по критерию (например: «чаще всего красный —
  наполнение витрины» vs «чаще всего красный — приезд водителя»), в идеале мини-чарт.

### 6.2. Таблица-радар по всем лавкам
- Строки — лавки, столбцы — дни (как в легаси-листе на конкретную лавку, но по всей
  сети сразу), ячейка — цветной статус.
- Фильтры: локация/регион (`Регион` из `Витрины.xlsx`), роль/критерий, диапазон дат,
  статус (показать только 🔴 и т.д.).

### 6.3. Карточка лавки (drill-down)
- Клик по лавке → раскрывается история по дням: время отметки каждого сотрудника,
  водителя, % наполнения витрины, финальный статус по каждому критерию + что именно
  повлияло (см. п.5.4 про логирование расчёта).

### 6.4. Роли на дашборде
Учитывай явно (включая стажёров как модификатор, не отдельную роль в фильтрах, если
не скажешь иначе): Повар, Повар-стажёр, Кассир, Кассир-стажёр, Бариста, ЗД по залу
(замдиректора по залу), Водитель-экспедитор. `[ПОДТВЕРДИ]`: точный список должностей —
сверь с HR-справочником, в тестовых файлах могут быть не все.

## 7. Стек и архитектура (рекомендация, не догма)

- **Next.js (TypeScript) full-stack** — одно приложение, API routes для бэкенда,
  React для дашборда. Быстрее всего собрать MVP за день.
- **БД**: начни с SQLite (файл, ноль инфраструктуры) для MVP, оставь миграцию на
  Postgres как TODO — за неделю доработки, когда данных станет больше и появится
  многопользовательская запись.
- **ETL**:
  - Job #1 (раз в день, дедлайн 09:30): скачать последние версии `выходы.xls` и
    `водители.xls` с Google Диска → распарсить (`xlrd`/`SheetJS`, файлы старого
    формата `.xls`, не `.xlsx`) → посчитать статусы по алгоритму п.4–5 → записать в БД.
  - Job #2 (каждые 10 минут + вручную по кнопке «Обновить» в UI): читать Google
    Таблицу наполненности через Google Sheets API → пересчитать статус по порогам →
    апдейт в БД.
- **Авторизация к Google API**: сервис-аккаунт с доступом на чтение к папке на Диске
  и к таблице (сервис-аккаунт должен быть добавлен как редактор/читатель в саму
  таблицу и папку — это сделает Горностай вручную после того, как Claude Code выдаст
  email сервис-аккаунта).
- **Хостинг**: Vercel для MVP (быстрый деплой, встроенный крон через Vercel Cron) —
  либо самостоятельный VPS (виртуальный сервер), если нужен полный контроль/деньги на
  Vercel не выделены. `[ПОДТВЕРДИ]`: куда деплоим.
